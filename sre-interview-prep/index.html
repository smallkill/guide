2. Kubernetes(重點)

30 秒框架(架構)
  • Control plane:API Server(唯一入口)、etcd(狀態)、Scheduler(排程)、Controller Manager(調節迴圈)。
  • Node:kubelet(執行 Pod)、kube-proxy(Service 轉發)、container runtime。
  • 核心哲學:宣告式 + reconciliation loop——你宣告期望狀態,controller 不斷把實際狀態拉回去。
展開版:核心物件
  • Deployment:管理無狀態應用的 ReplicaSet,支援 rolling update / rollback(kubectl rollout undo)。
  • Service:ClusterIP(叢集內)、NodePort(節點埠)、LoadBalancer(雲端 LB 對外);用 label selector 找 Pod,提供穩定 endpoint。
  • Ingress:L7 路由,一個入口按 host/path 分流到多個 Service,搭配 Ingress Controller(nginx/traefik)與 TLS 終結;比每個服務各開一個 LB 省成本。
  • 其他常考:ConfigMap/Secret(設定與機敏分離)、StatefulSet(有狀態)、DaemonSet(每節點一份,常用於 log/監控 agent)、HPA(自動水平擴縮)。
展開版:RBAC
  • 四件組:Role / ClusterRole(定義能對哪些資源做哪些動詞)+ RoleBinding / ClusterRoleBinding(綁到 user / group / ServiceAccount)。
  • 原則:最小權限、namespace 隔離、CI/CD 用專屬 ServiceAccount 而不是 admin kubeconfig、定期用 kubectl auth can-i --list 稽核。
展開版:Release 規則怎麼制定
可以這樣講:「我會把上線規則定成四層:① 進 pipeline 的門檻——code review + 自動化測試 + 安全掃描全綠才能進 staging,這是我在 Moxa 實際建立過的紀律,Coverity/Nessus 掃不過就是不能出;② 部署策略——預設 rolling update 設好 maxSurge/maxUnavailable,重要服務用 canary 先切一小部分流量觀察指標;③ 觀察窗——上線後盯 error rate 和 latency,超過閾值自動或手動 rollback,Deployment 天生支援 rollout undo;④ 節奏——固定 release window、freeze period、每次上線有 owner 和 rollback plan。」
誠實回答(開場就明講,不要等被追問):「先誠實說:我工作上沒有用過 Kubernetes,正式環境的容器經驗是 Docker + 雲端託管服務(GCP、Cloudflare)。上面講的架構和物件模型是我為了補這塊系統性學的,不是實戰經驗,細節實務坑我還沒踩過。但我有把握短時間上手,理由有二:一,K8s 的核心就是宣告式 + reconciliation,跟我天天在用的 Terraform 是同一套思維;二,我的履歷就是三次跨域紀錄——嵌入式跨到 AWS 從零建車隊平台、再跨到韌體 CI/CD、再到現在的 GCP,每次都是三個月內接手上線。如果加入,我的計畫是先從 managed K8s(GKE)+ 現有 manifest 讀起,搭配資深同事 review 我前幾次的變更。」

3. Cloud Infrastructure(重點)

30 秒框架(架構設計)
  • 分層:邊界(CDN/WAF/LB)→ 應用層(無狀態、可水平擴)→ 資料層(managed DB + 備份/replica)。
  • 原則:multi-AZ 高可用、IaC(Terraform)全部進版控、最小權限 IAM、私有子網 + 明確出入口。
  • 親身:AWS 從零建車隊平台(EC2/S3/Lambda/IoT Core/API GW/KVS);現職 GCP + Terraform。
展開版:DDoS / 惡意流量應對
  • 事前(架構性防護):CDN + Anycast 吸收 L3/L4(CloudFront/Cloud Armor/Cloudflare)、WAF 擋 L7(SQLi/XSS/bot)、rate limiting、autoscaling 保底、源站藏在 LB 後面不暴露真實 IP、關閉不必要的 port。
  • 事中:先從監控確認攻擊型態(流量暴增?特定 endpoint?特定來源?)→ WAF 上臨時規則(封 IP 段/GeoIP/加驗證挑戰)→ 必要時啟動雲端 DDoS 進階防護(AWS Shield Advanced / Cloud Armor)。
  • 事後:檢討 rate limit 閾值、把臨時規則固化進 IaC、寫 postmortem。
  • 親身:「我自己的公開服務全部掛在 Cloudflare 後面,API 有做 rate limiting——我還特地對自己的站跑過六階段安全稽核,把發現的低風險項全部修掉,包含對統計 endpoint 加限流。」
展開版:雲端安全設計
  • 網路:VPC 分公私子網,DB/內部服務不給公網 IP;security group 白名單思維。
  • 身分:IAM 最小權限、服務用 service account/role 不用長期金鑰、金鑰進 secret manager 不進 code。
  • 變更:全部走 Terraform + review,禁止 console 手改(drift 會咬人)。
  • 資料:傳輸 TLS、儲存加密、備份定期演練還原。

4. Monitoring & Observability

30 秒框架
  • 三支柱:Metrics、Logs、Traces;規劃從「使用者感受」出發定 SLI/SLO,再往下鋪基礎設施指標。
  • 兩套經典指標框架:Google 四大黃金訊號(Latency/Traffic/Errors/Saturation)、主機層 USE(Utilization/Saturation/Errors)。
  • 工具:Prometheus + Grafana + Alertmanager 為標準組合;log 用 Loki/ELK;雲端原生用 CloudWatch/Cloud Monitoring。
展開版
可以這樣講:「我規劃監控會從上往下三層:最上層是使用者體驗——error rate、p95/p99 latency、availability,這是定 SLO 用的;中層是應用指標——QPS、queue depth、慢查詢;底層是基礎設施——CPU、memory、disk I/O、network、還有容易被忘記的 inode 和 file descriptor。告警只對『需要人採取行動』的東西發,而且對 symptom 告警優先於對 cause 告警,不然會告警疲勞。我的親身例子:我自架的 SaaS 監控是自己從 request log 建的——每個請求寫進分析資料庫,watchdog 定時算真實 error rate 和 p95 latency,超標就透過 Telegram 通知我。做這件事讓我踩過一個很實際的坑:取樣型的監控資料算 percentile 必須用取樣間隔加權,不然 p95 會失真——這種細節只有真的自己建過才會知道。另外我在自駕車時期建過 13 台車的即時監控平台,那是車輛狀態 + 位置 + 視訊流的多維度監控,對『什麼指標才真正代表健康』很有感。」

常見追問:

  • Prometheus 架構:pull-based scrape /metrics、exporter 生態(node_exporter 等)、PromQL、Alertmanager 做分組/靜默/路由。
  • 告警設計:基於 SLO burn rate 而非單點閾值;分級(page vs ticket);每條告警要有 runbook。

5. Incident Troubleshooting(情境題)

30 秒框架
  1. 先看「使用者受影響了嗎、多大範圍」——error rate、latency、availability 儀表板。
  2. 先止血再找根因:rollback、切流量、擴容都是合法的第一步。
  3. 定位:對照「最近改了什麼」(deploy/config/infra 變更)→ 逐層縮小(LB → app → DB → infra)。
  4. 事後:blameless postmortem + action item 進追蹤。
展開版
可以這樣講:「異常發生時我第一步看的是 symptom 面的三個數字:error rate、p95 latency、traffic——先回答『使用者現在有沒有受影響、影響多廣』,這決定嚴重度和要不要先止血。第二步問『最近改了什麼』,因為多數 incident 是變更引起的,能 rollback 就先 rollback,恢復服務優先於找根因。第三步才逐層定位:從入口往下——LB 的 5xx 分佈是全部服務還是單一服務?單一服務就看它的日誌和資源(CPU/mem/FD);像 DB 的話看連線數和慢查詢。過程中留時間軸紀錄,事後寫 blameless postmortem,重點是 action item——監控缺口補監控、流程缺口補自動化。我在 Moxa 的習慣就是這樣養的:CI 整合問題我們靠自動化提早最多 7 天抓到,就是把『事後救火』改成『事前攔截』的例子。」

7. Security(重點)

30 秒框架
  • 總綱:Defense in depth + 最小權限 + Shift-Left(安全做進 pipeline,不是事後稽核)。
  • Cloud:IAM role 化、無長期金鑰、私網隔離、加密、audit log。
  • K8s:RBAC、NetworkPolicy、Secret 管理、image 掃描、Pod 安全(non-root)。
  • LB:TLS 終結 + 現代 cipher、WAF、rate limit、health check 不洩漏資訊。
展開版
可以這樣講:「我對安全的核心信念是 Shift-Left——這是我在 Moxa 實際落地過的:把 Coverity 和 Nessus 整合進日常 CI,漏洞在開發階段就攔截,而且做到不拖慢開發節奏,這個平衡才是難的。現職也是把安全檢查和漏洞掃描整合進 CI/CD 管線確保合規。Cloud security 面:IAM 最小權限、服務間用 role/service account 不留長期金鑰、機敏值進 secret manager、DB 絕不暴露公網、所有變更走 Terraform 留審計軌跡。K8s security 面:RBAC 最小權限、namespace 隔離、NetworkPolicy 預設拒絕再開白名單、container 以 non-root 跑並用 image scanning(Trivy)進 CI。LoadBalancer 面:TLS 1.2+ 與強 cipher、HTTP 強制轉 HTTPS、WAF + rate limiting 放在 LB 層、後端 security group 只收 LB 來的流量。我還會主動對自己的服務做攻擊面盤點——我對自己的 side project 跑過完整安全稽核並把所有發現修掉,包括對外 API 補 rate limiting。」

Q1. Too many open files 排查與解決

30 秒框架
  1. 確認限制:ulimit -n(process)、/proc/sys/fs/file-max(系統)。
  2. 找兇手:lsof 統計哪個 process 開最多、開的是什麼(socket? log? 沒關的檔?)。
  3. 對症:是 FD leak 就修程式;是正常高負載就調 limit(systemd LimitNOFILE / limits.conf / sysctl)。
展開版 + 指令 
# 目前 process 的 FD 上限(soft/hard)
ulimit -n
ulimit -Hn
# 針對已在跑的 process
cat /proc/<PID>/limits | grep "open files"
ls /proc/<PID>/fd | wc -l          # 該 process 實際開了幾個

# 系統層
cat /proc/sys/fs/file-max           # 全系統上限
cat /proc/sys/fs/file-nr            # 已分配 / 未用 / 上限

# 誰開最多?開了什麼?
lsof | awk '{print $1, $2}' | sort | uniq -c | sort -rn | head
lsof -p <PID> | head -50            # 看類型:REG(檔案)/ sock / pipe

# 解法
# 1) 暫時:ulimit -n 65535(當前 shell)
# 2) 永久(login):/etc/security/limits.conf → user soft/hard nofile 65535
# 3) systemd 服務:unit 檔 [Service] LimitNOFILE=65535 → daemon-reload + restart
# 4) 系統層:sysctl -w fs.file-max=... + /etc/sysctl.conf
收尾要講:「調大 limit 只是止血——重點是判斷這是『合理的高並發』還是 FD leak。如果 lsof 看到一堆 CLOSE_WAIT socket 或同一個 log 檔開了幾千次,那是程式沒關 FD,調 limit 只會延後爆炸,要回頭修 code。然後把 FD 使用率加進監控,下次在爆之前告警。」

Q2. 建置 Kubernetes 要設定哪些重要項目

30 秒框架
  • Control plane 高可用 + etcd 備份;網路(CNI、Pod/Service CIDR 規劃)。
  • 安全:RBAC、NetworkPolicy、Secret 加密、audit log。
  • 資源治理:requests/limits、ResourceQuota、LimitRange、node pool 規劃。
  • 可運維:監控 + log 收集、Ingress、儲存(StorageClass)、升級與備份策略。
展開版(檢查清單式回答)
  • 叢集拓撲:control plane 至少 3 節點跨 AZ(或直接用 managed:GKE/EKS);etcd 定期 snapshot 備份並演練還原。
  • 網路:選 CNI(Calico/Cilium);Pod CIDR、Service CIDR 事先規劃不可與 VPC 重疊;DNS(CoreDNS)資源配足。
  • 安全:RBAC 最小權限 + 停用匿名存取;NetworkPolicy 預設 deny;Secret 啟用 encryption at rest;API server audit logging;node 定期升級補丁;image 私有 registry + 掃描。
  • 資源治理:所有 workload 設 requests/limits(不設會互相踩死、也讓 scheduler 失準);namespace 級 ResourceQuota;系統元件保留資源(kube-reserved/system-reserved)避免 kubelet 被餓死。
  • 可運維:metrics-server + Prometheus/Grafana;log 用 DaemonSet 收(Fluent Bit);Ingress Controller + cert 管理(cert-manager);StorageClass 與 PV 回收策略;升級走 node pool 滾動 + PodDisruptionBudget 保住可用性。
  • 交付流程:manifest 全部進版控(Helm/Kustomize),搭配 GitOps(ArgoCD)——「這對我來說是 Terraform 同一套宣告式思維」。
誠實回答:開頭直接說「我沒有實際建置過 K8s,以下是我準備時整理的檢查清單,用我做 IaC 和 managed service 的架構觀來回答」——先講清楚是知識不是經驗,再展現架構觀。被追問任何沒把握的細節就明說「這塊我沒實際操作過,我的理解是⋯」,絕不硬掰。

Q3. 硬碟容量充足但檔案無法存取

30 秒框架(依機率排序)
  1. inode 用光——df -h 有空間但 df -i 100%(大量小檔案)。
  2. 權限/屬性——ownership、mode、immutable flag、SELinux/AppArmor。
  3. 檔案系統層——read-only remount(fs error)、mount 掛掉(NFS stale handle)、fs 損毀。
  4. 其他——被 deleted 但仍被 process 佔住、quota 限制、FD 上限(接回 Q1)。
展開版 + 指令 
df -h; df -i                 # 空間 vs inode ← 經典陷阱,先看這個
# inode 滿:找小檔案大戶
du --inodes -d 3 / 2>/dev/null | sort -rn | head   # 常見:session 檔、cache、mail queue

ls -la file; lsattr file     # 權限 + immutable(i flag 會讓 root 也寫不進)
# SELinux:ls -Z、ausearch -m avc;AppArmor:dmesg

mount | grep ro,             # 檔案系統被 remount 成 read-only?
dmesg | grep -iE 'error|ext4|xfs|I/O'   # fs/disk 錯誤 → fsck(unmount 後)
# NFS:Stale file handle → remount

lsof +L1                     # deleted 但仍被佔住的檔案(空間假象的另一半)
quota -u user; xfs_quota     # user/group quota
答題姿態:先講「df -h 跟 df -i 我會一起看」——這題八成就是在考 inode。然後展開權限/immutable/read-only remount/NFS,展現排查是有層次的,不是背答案。

Q4. DB Response Time 慢的排查與調校

30 秒框架
  1. 先分層:是 DB 真的慢,還是網路/連線池/應用層慢?(從 app 端和 DB 端各量一次)
  2. DB 端:slow query log 抓慢 SQL → EXPLAIN 看執行計畫 → 缺 index?全表掃?
  3. 資源與並發:CPU/IO/記憶體、連線數、lock 等待。
  4. 調校:index、SQL 改寫、連線池、read replica、cache、參數(buffer pool)。
展開版 + 指令 
-- MySQL
SHOW PROCESSLIST;                          -- 現在誰卡著、state 是什麼
SET GLOBAL slow_query_log=ON; SET GLOBAL long_query_time=1;
EXPLAIN SELECT ...;                        -- type=ALL 全表掃 / rows 過大 / 沒用到 index
SHOW ENGINE INNODB STATUS\G                -- lock wait、deadlock
SHOW GLOBAL STATUS LIKE 'Threads_connected';
-- PostgreSQL:pg_stat_activity、pg_stat_statements、EXPLAIN (ANALYZE, BUFFERS)

# OS 層(DB 主機)
iostat -x 1        # %util、await 高 → disk 瓶頸
vmstat 1           # si/so 有值 → 在 swap,記憶體不夠
top                # CPU bound?
  • 常見根因排序:缺 index / index 沒被用(隱式轉型、函數包欄位)→ 慢 SQL(N+1、大 offset 分頁)→ lock 競爭 → buffer pool 太小 → 連線數爆(沒連線池)→ disk IO 飽和。
  • 架構級解法:read replica 分流讀、cache(Redis)擋熱點查詢、批次寫入、資料歸檔瘦身大表。
  • 預防:把 slow query 數、p95 query latency、連線數、replication lag 放進監控,慢化趨勢在使用者抱怨前就看到。

Q5. 平時用哪些 Monitoring 工具、監控哪些指標

30 秒框架
  • 工具:Prometheus + Grafana + Alertmanager(metrics)、Loki/ELK(logs)、雲原生 CloudWatch / Cloud Monitoring;uptime 外部探測。
  • 指標分三層:基礎設施(CPU/Mem/Disk/Net/inode/FD)→ 應用(QPS、error rate、p95/p99、queue)→ 業務 SLO。
  • 親身:自建 watchdog 監控真實 error rate 與 p95 + Telegram 告警。
展開版
層指標為什麼
InfraCPU(含 load、iowait)、Memory(含 swap)、Disk(容量、inode、IO util/await)、Network(頻寬、錯包、連線數)、FD 使用率USE 法:利用率/飽和度/錯誤;inode 和 FD 是最常被漏掉、爆掉最痛的兩個
AppQPS、error rate、latency p50/p95/p99、queue depth、慢查詢數、GC/thread四大黃金訊號;平均值會騙人,一定看 percentile
SLOavailability、error budget 消耗速度告警基於 burn rate 而不是單點閾值,減少 noise
親身例子:「工具鏈上我實際用過雲端原生監控(AWS 時期建車隊監控、現職 GCP 環境),也自己造過輪子:我的 side project 每個 request 都寫進分析資料庫,watchdog 定期算真實 error rate 和 p95 latency,異常直接推播到我手機。自己建過一次之後,對『取樣資料算 percentile 要加權』『告警閾值怎麼定才不會吵』這些都有實感。」

Q6. Linux 查 CPU / Memory 等資源的指令

30 秒框架

綜覽 top/htop → CPU 細看 vmstat/mpstat/uptime → 記憶體 free -h → 磁碟 iostat/df/du → 網路 ss/sar → 針對單一 process 用 pidstat/ps。

展開版 + 指令 
top / htop            # 綜覽:load、%us/%sy/%wa、每 process CPU/MEM
uptime                # load average 1/5/15 min(對照 CPU 核數)
vmstat 1              # r(runnable 排隊)、si/so(swap!)、wa(IO wait)
mpstat -P ALL 1       # 每顆核心分佈(單核吃滿 vs 平均)

free -h               # 重點看 available;buff/cache 是可回收的,別誤判
cat /proc/meminfo
ps aux --sort=-%mem | head    # 記憶體大戶
# OOM 檢查:dmesg | grep -i "out of memory"

iostat -x 1           # %util、await、r/s w/s → disk 瓶頸
df -h; df -i; du -sh /* 2>/dev/null | sort -rh | head

ss -tulnp             # 聽哪些 port、誰在聽
ss -s                 # socket 統計(TIME_WAIT 過多?)
sar -n DEV 1          # 網卡吞吐

pidstat -p <PID> 1    # 單一 process 的 CPU/mem/IO 時間序列
加分講法:「我不會只背指令,我有一套順序:先 uptime + top 判斷是 CPU、memory 還是 IO 型的問題——%wa 高就往 iostat 走,si/so 有值就往記憶體走。free 的重點是 available 而不是 free,buff/cache 是可回收的——很多人看到 free 很小就誤判記憶體不足。」

Q7. 如何確認 Service 存活並持續提供服務(Health Check)

30 秒框架
  • 層次:process 活著 ≠ port 有開 ≠ 能正確回應 ≠ 依賴(DB)健康——health check 要分深淺。
  • 手段:systemd/K8s probe 自動重啟 + LB health check 摘除壞節點 + 外部 uptime 探測 + 持續性靠監控告警。
  • K8s 三 probe:liveness(掛了重啟)、readiness(沒準備好就不收流量)、startup(慢啟動保護)。
展開版 + 指令 
# 手動逐層驗證
systemctl status myservice          # process 層
ss -tlnp | grep :8080               # port 層
curl -sf -m 3 http://localhost:8080/healthz ; echo $?   # 應用層
curl -w "%{http_code} %{time_total}\n" -o /dev/null -s URL  # 帶延遲

# 自動化
# systemd:Restart=on-failure + WatchdogSec
# K8s:
#   livenessProbe  → 失敗達 failureThreshold 就重啟容器
#   readinessProbe → 失敗就從 Service endpoints 摘掉,不收流量
#   startupProbe   → 啟動慢的服務先豁免 liveness
  • Endpoint 設計:/healthz 淺檢查(process 能回應)給 liveness;/ready 深檢查(DB/依賴可用)給 readiness——深檢查不要放 liveness,不然 DB 抖一下整排 Pod 被連環重啟。
  • 「持續」提供服務:單次 check 只證明當下活著;持續性靠外部 uptime 探測(從使用者視角打)+ error rate/latency 監控 + LB 自動摘除,三者合起來才是完整答案。
  • 親身:「我的 side project 就是這樣做的:watchdog 持續驗證服務真實回應品質(error rate/p95),而不是只 ping 一個 endpoint;自駕車時期更極端——車輛掉線幾秒就是安全事件,所以 heartbeat + 斷線告警是設計核心。」
